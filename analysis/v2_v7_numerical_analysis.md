# Converse2D v2–v7 数值不一致分析

本文记录修复前的历史源码分析；后续实现、GPU 验证与性能结果见 [修复验证报告](gpu_validation.md)。

分析日期：2026-09-11。当前工作区 main 为 `c7eb880`。

结论：差异包含明确的算子语义错误、梯度路径缺失、缓存失效问题，以及原闭式公式自身的浮点消减误差。最大的前向分歧从 v3 的频谱索引改动开始；v7 又引入了不等价的计算域转换。不能仅用“CUDA 精度不同”解释。

## 分析范围与验证方式

- `207e214`：保留原始 v2–v7 全套源码，作为逐版比较基准。
- `9f9e2f8`：核查训练时绕过缓存后的完整版本；v3–v6 的核心索引问题仍在。
- `2197378`：核查曾经尝试的 v7 `ortho` 修改。
- `6353910`、`eac211b`：核查 v7 的半谱加权修复尝试。
- `c7eb880`：当前 main，仅保留 ATen C++ 实现。
- `c789554`：现有 `codex/numerically-stable-closed-form` 分支上的残差公式修改。

这里的 v2–v7 指历史 README 中的 CUDA 优化序列；`origin/dev2` 的重新组织版本没有 v7，不与上述序列混用。

源码经 Git 只读检查。复现实验使用 NumPy 2.3.5、SciPy 1.16.3，在 CPU 上重现原代码的索引和数学运算。当前默认 Python 未安装 PyTorch，未编译运行历史 CUDA 扩展，因此下面数字是数学语义复现结果，不是原 GPU 内核误差实测，也不覆盖具体 CUDA 流或编译器问题。

复现命令：`python analysis/v2_v7_numerical_audit.py`。结果见同目录 `v2_v7_numerical_results.json`。

## 1. v2 → v3：频谱分组的索引被改错

设高分辨率频谱尺寸为 `(Hs, Ws)=(H*s, W*s)`。

v2 的 `view(s,H,s,W) → permute → mean` 实际计算：

```text
M(A)[h,w] = sum(A[h+i*H, w+j*W] for i,j in 0..s-1) / s²
```

它把频谱分成 s×s 个大块，平均每块中的对应位置。

v3 CUDA 则使用 `hi0=ho*s`、`wi0=wo*s`，实际计算：

```text
P(A)[h,w] = sum(A[h*s+i, w*s+j] for i,j in 0..s-1) / s²
```

这是相邻小块平均。两个运算的输入分组不同，float64 也不会一致。

用按行排列的 0–15 构成 4×4 矩阵，s=2：

```text
v2：[[5, 6],       v3：[[2.5, 4.5],
     [9,10]]            [10.5,12.5]]
```

源码位置：`9f9e2f8:Converse2D/torch_converse2d/converse2d_v3_kernels.cu:46`。v4/v5 同类代码在第 169 行，v6 在第 171 行。

## 2. v3 同时把整块平铺改成逐元素重复

v2 的 `repeat({1,1,s,s})` 对低分辨率频谱做周期平铺：

```text
E(Q)[h,w] = Q[h % H, w % W]
```

v3 的 `view(B,C,H,1,W,1).expand(B,C,H,s,W,s).reshape(...)` 实际是：

```text
E_wrong(Q)[h,w] = Q[h // s, w // s]
```

例如 `Q=[[1,2],[3,4]]`、s=2：

```text
v2 repeat           v3 expand
1 2 1 2             1 1 2 2
3 4 3 4             1 1 2 2
1 2 1 2             3 3 4 4
3 4 3 4             3 3 4 4
```

源码位置：`9f9e2f8:Converse2D/torch_converse2d/converse2d_v3.cpp:152`；v4/v5/v6 对应第 144/181/145 行。

两处错误需要一起修复。正确的逻辑广播形状应为 `Q.view(B,C,1,H,1,W).expand(B,C,s,H,s,W)`；若随后 reshape 为普通连续张量，仍可能发生实际复制，不能仅凭使用 expand 就认定省去了内存分配。

正确归约的反向也应按周期平铺 `grad_out/s²`，而非复制到相邻 s×s 小块。现有 backward 对应的是错误的局部平均算子；它可能通过自身 gradcheck，但仍不等于原算法的梯度。

## 3. v4、v5：继承前面的错误，新增优化不是主要根因

v4 的零插值 CUDA 写入 `out[h*s,w*s]=x[h,w]`，其余位置由 zeros 初始化，与 v2 语义一致。

v5 将 `(B,C,H,W)` reshape 为 `(B*C,H,W)` 后只在最后两维 FFT，数学上也等价。实际 FFT 执行路径是否变化需 GPU 测量，不能据此断言必然发生精度下降。

因此 v4/v5 对 v2 的大误差首先应归因于继承的归约与平铺索引，而非零插值或合并 batch 维度。

## 4. v6：额外存在权重梯度路径缺失

`fb_postprocess_cuda` 创建 `empty_like`/`empty`，然后用裸 CUDA kernel 写入 FBC 与 F2B，未通过自定义 autograd Function 为该操作定义反向。

因此 `FBC=conj(FB)`、`F2B=|FB|²` 对 FB 的依赖没有记录到计算图。FB 在其他表达式中仍有直接依赖，所以 weight 梯度可能有值，但缺失部分链式求导项；“有梯度”不能证明梯度正确。

源码位置：`9f9e2f8:Converse2D/torch_converse2d/converse2d_v6.cpp:83`，以及 `converse2d_v6_kernels.cu:297` 起。

v6 将 `abs(FB).pow(2)` 改成 `real²+imag²`，两者数学相等、浮点舍入路径不同。不能笼统认为后一种更不准确；小差异会被后续除以很小的 lambda 放大。v3–v6 的 `1.0f/(s*s)` 还会把 float32 舍入带入 double 路径，s=3 时尤其可见，但远小于索引错误造成的偏差。

## 5. v7：空间域除法不等于频域除法

原算法在频域计算：

```text
FBR  = M(FB * FR)
invW = M(|FB|²)
Q    = FBR / (invW + lambda)
```

早期 v7 先对 `FB*FR`、`|FB|²` 做 irfft，再在空间域 pooling、相除，之后 FFT 回去。傅里叶变换不保持逐元素除法，因此这不是 rFFT 对全 FFT 的等价替换。

即使 s=1、不再涉及归约索引，v7 依然算错。原来的非负频域分母 `|FB|²+lambda` 被替换成空间域自相关值加 lambda；其值分布完全不同，随机样例中会导致非常大的输出。

源码位置：`9f9e2f8:Converse2D/torch_converse2d/converse2d_v7.cpp:162` 起。

`2197378` 将 FFT/IFFT 一起改成 ortho 也不构成修复：如果采用单位正交变换 U，循环卷积满足 `U(k*x)=sqrt(N)*U(k)*U(x)`。直接把 PSF 频谱也缩小为原来的 `1/sqrt(N)`，却不补偿卷积乘子的尺度，会改变数据项与 lambda 的相对关系。

`6353910`、`eac211b` 的 weighted-block 修复将运算放回半频谱，但仍采用 `ho*s+di, wo*s+dj` 的相邻索引，并以内部频率权重 2、DC/Nyquist 权重 1 进行平均。该权重不能代替跨混叠频率分组；对于复数频谱还需要共轭恢复及二维镜像索引。后续 expand 仍为逐元素重复。所以该修复在 s=1 可以等价，s>1 仍不成立。

此外，原始 v7 若开启 `CONVERSE2D_USE_CUDA_KERNELS`，裸 launcher 没有把定义的 backward 接入 autograd；默认 setup 未定义该宏，实际走 ATen fallback。需要区分这两条路径，不能一概归因为 CUDA backward。

## 6. v2–v7 的缓存问题要区分历史与当前状态

早期缓存 key 包含设备编号、dtype、通道、目标尺寸与 `psf.data_ptr()`，没有权重的版本号或内容身份。

- optimizer 或 copy_ 原地更新权重后，地址未变，旧 FB/F2B 仍可能命中。
- 缓存带计算图的 FB，会让下一次 backward 重用已释放的图；若第一次在 no_grad 中构建缓存，后续训练也可能缺失权重梯度。
- 释放权重后地址被复用，也存在误命中风险。

`944c42c` 为 v3–v7 加入训练时绕过缓存，`9f9e2f8` 为 v2 加入同类逻辑。当前 main 也有该保护，所以不能把早期训练缓存问题直接当成当前 main 必然发生的行为。

当前 main 的推理缓存仍缺少权重版本：先 no_grad 推理，原地加载或修改权重，再对同形状推理，仍可能拿到旧频谱。仅补版本号还不完全解决新张量复用旧地址的问题，需要可靠的张量身份与缓存生命周期管理，或在权重变化时显式清空。

## 7. 原始闭式公式本身会放大舍入误差

所有这些版本基本沿用 `FX=(FR-FBC*Q)/lambda`。

当 bias=0、eps=1e-5：

```text
lambda = sigmoid(-9) + 1e-5 = 1.33394576e-4
1/lambda = 7496.56
```

分子两项接近时会发生消减，分子的绝对误差随后乘以约 7497。这是误差传播系数，不表示所有输出误差都严格放大同一倍数。

这解释了修正算子语义后，FFT、求和顺序、模平方实现的微小区别为什么仍可形成约 1e-4–1e-3 的输出差异。它不能解释或修复 v3/v7 的数学错误。

令 `Y=FFT(x)`、`X0=FFT(x0)`，正确归约为 M，正确平铺为 E，则等价残差式为：

```text
FX = X0 + conj(FB) * E((Y - M(FB*X0)) / (M(|FB|²) + lambda))
```

该表达式避免末尾的“大数相减再除小数”。现有 `c789554` 分支已采用这一方向；当前 main 尚未应用。它不能代替对历史 CUDA 索引和梯度路径的修复。

## 8. 可重复实验结果

固定随机种子 20260911，输入 8×10、3×3 softmax 型正核、bias=0、eps=1e-5。无 padding，直接比较算子核心，所有版本输入一致。

下表为 float64 下对 v2 的最大绝对差：

| 路径 | s=1 | s=2 | s=3 |
|---|---:|---:|---:|
| v3 语义（v4/v5 继承） | 0 | 6.652e3 | 5.799e3 |
| v6 前向语义 | 1.108e-12 | 6.652e3 | 5.799e3 |
| 原始 v7 | 2.295e7 | 1.517e7 | 1.098e7 |
| weighted 修复 v7 | 2.304e-15 | 6.301e3 | 5.653e3 |
| 正确残差式 | 1.665e-12 | 1.156e-12 | 8.220e-13 |

float32 输入先量化，再以相同输入的 float64 残差式为参考：

| 公式 | s=1 | s=2 | s=3 |
|---|---:|---:|---:|
| v2 原式最大绝对误差 | 1.033e-3 | 5.620e-4 | 4.912e-4 |
| 残差式最大绝对误差 | 2.744e-6 | 8.281e-7 | 6.100e-7 |

这些样例足以反证数学等价性；误差大小不是对所有模型或 GPU 的普遍上界。

## 9. 为什么原来的测试没有证明一致性

`207e214:test/test_speed.py:148` 仅断言 `x.grad is not None`。CSV 的 `grad_ok=True` 表示反传没有在该检查处失败，并不比较梯度值，更不检查 weight/bias 梯度是否正确。CUDA benchmark 的 weight/bias 没有设置 requires_grad。

另外，PyTorch 和 CUDA 分支的随机数消费顺序不同；PyTorch 创建带 padding 的模块，CUDA 直接调用无 padding 的算子，计时结果也不对应完全相同的工作量。

当前 `test/test_error.py` 会比较前向与输入梯度，但只测试已安装的一个扩展；随机创建的 x0 未用于直接调用，且没有比较权重和 bias 的梯度。max relative error 在参考值接近零时也会放大，不能独立作为根因判断。

## 修复与验证优先级

1. 先以 v2/当前 PyTorch 的正确分组为参考，同时修正 v3–v6 归约、平铺及其反向。
2. 对 v7 保持运算在频域；s>1 必须正确处理半谱的共轭索引与混叠组，不能用空间 pooling 或局部加权平均替代。
3. 为 v6 后处理补齐 autograd，处理缓存生命周期和推理权重变化。
4. 再采用残差公式改善 float32 稳定性，避免靠放宽 tolerance 掩盖算法错误。
5. 用同一份 x/x0/weight/bias 比较全部前向及四类梯度，覆盖 s=1/2/3、奇偶空间尺寸、float64/float32、连续两次训练反传，以及 no_grad 权重更新后推理。对 s=1 的直接闭式解和 s>1 的小规模稠密线性求解也应建立独立参考。

本次只新增分析脚本、结果与报告，未修改生产实现、切换分支或安装依赖。
